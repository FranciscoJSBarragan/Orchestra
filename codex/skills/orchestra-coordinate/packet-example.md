# Project register and child packet

Illustrative fields, not executable instructions or a required persisted schema.
Use actual approved values and omit inapplicable fields. Keep secrets out.

## Register content

- Outcome and authority: link the approved brief, exclusions, budget/tier choices
  and exact implementation, commit, push, PR, merge or deployment grants.
- Repositories: identity, checkout owner, applicable instruction paths, and base
  revision. A project name alone is not a repository identity.
- Shared contract: the API/data/version behavior each child must consume;
  distinguish an agreed contract from an unresolved hypothesis.
- Joint acceptance: the real caller journey, expected behavior, verification
  environment and responsible executor. Link the reusable recipe where present.
- Children: logical task, route, host, exact session/task handle, checkout,
  selected task-root model/effort independently of parent and role resources,
  dependency condition, plan/result link and observed terminal SHA. Record a
  pending dispatch intent before starting a child, then its returned handle.
- Decisions and blockers: only material unresolved questions or changed shared
  assumptions; do not mirror every child finding or phase.

An interrupted `dispatch pending` row is ambiguous, not a license to create a
replacement. Reconcile with the host's existing tasks/sessions and Git.

## Child packet: service contract change

Role: task root for the named service, not a scoped implementation worker.
Route: full Orchestra, explicitly activated for this child by the approved
initiative. Tier: the user's selected supported tier. Repository and checkout:
exact identity/path; one named checkout creator. Adopt a supplied isolated
checkout, or establish managed isolation before any task/source writes when
launched from a shared directory. Approved product base: full SHA. Reconcile any
unexpected HEAD or host branch metadata before mutation.

Task-root resources: the explicit supported model/effort or accepted host default;
separate from the parent's selection and selected tier's role matrix. Resolve the
actual dispatch type and controls through [host transports](host-transports.md).

Instructions: pinned Orchestra revision or verified package identity; absolute
entry skill, workflow, runtime/skills roots, selected matrix and spawn reference.
Product base, instruction revision and environment build are separate identities.

Objective: implement the approved response contract for the consumer named in
the shared brief. Scope/exclusions: exact affected areas, allowed operational
documentation, and behaviors that must remain compatible. Evidence: current
base SHA and only relevant context/recipe paths. Dependencies: the agreed
contract version; do not read a concurrently changing sibling checkout.

Source-writing policy: resolve the selected runtime and skills roots and name
the absolute [Source comments](../orchestra/references/architecture_guidance.md#source-comments)
path in this child packet, including when selecting a custom workflow.

Retention: accessible durable result/review paths and exact revision transfer;
name any task-branch push grant or authorized held-result destination. Verify
access across environments rather than sharing an unreadable VM-local path.

Authority: implementation and reviewed phase commits already granted. Any
publication authority is listed separately with its repository, branch and
operation; absence means hold. Reuse this approval for reversible decisions
inside the objective. Ask the parent only for a material expansion or unresolved
product decision. Host permissions are unchanged.

Ownership: you own this child plan, implementation/review loop and resources.
Other children own their checkouts. Do not coordinate the initiative, spawn new
sibling roots or overwrite their work. Use ordinary role agents only if the
selected route and available host support them. Report the actual child handle
and plan location; no memory API is granted by this packet.

Handoff: exact repository, checkout, base and final full SHA; completed behavior;
required checks and independent review evidence (or explicit missing evidence);
recipe/evidence paths; remaining assumptions, blockers and delivery state;
cleanup or exact retained-resource handoff. Return a compact summary, with links
to full child evidence. Process exit alone is not acceptance.

## Repair packet

Before delivery, resume the same handle and checkout. After delivery, create
a bounded repair task from the delivered base under the existing scope and
separately applicable delivery authority; preserve the old evidence. State the child's current SHA, the failing
combined scenario and evidence, accepted correction scope, unchanged authority,
and affected dependency revisions. The child updates its own affected plan and
review/check evidence. The parent then replaces the old accepted SHA and reruns
the affected combined checks; it retains unrelated still-valid evidence.

## Pending task base-refresh packet

Continuation of the same child handle, still awaiting delivery. Current task HEAD:
full SHA. Actual authorized target base and new full SHA: exact values, preserving
legitimate local base commits for local integration. Reason: the named sibling
was delivered or the target otherwise moved. Unchanged acceptance/authority and
changed dependencies: bounded references. Apply WORKFLOW "Base refresh before
delivery", reuse the reviewer for the affected delta, and report the accepted
new SHA with refreshed evidence. This packet does not grant delivery into the base.
