# Example: create a note

This is an illustrative shape, not a recipe to copy into an unknown project.
Replace examples with discovered commands and observed routes; omit fields
that have no consumer. The index names the mapped scope and links to maintained
entries. It never implies that unmapped or unexecuted behavior passed.

## Behavior and entry points

A user creates a note from the toolbar or keyboard shortcut, saves it, and can
reopen its persisted contents. Link the product requirement or accepted behavior
that defines success; source code locates the implementation, not its correctness.
Name materially different entry points and relevant empty/error behavior.

## Prerequisites and drive

Reference canonical launch and readiness instructions from the index. Name safe
fixture data, authentication category, and the observable baseline. Give actual
commands or stable UI handles, including how to identify the intended build and
instance. Shared ports, data stores, and device limitations belong here.

## Expected result and proof

Capture the creation action and result, then reopen or independently read the
saved note. Reference existing automated tests where they establish part of the
behavior. Describe manual or environment-dependent gaps without storing a
permanent pass/fail scoreboard. Each run records its own revision and evidence.

## Recovery and cleanup

Describe reset from a failed attempt and removal of the run's disposable note.
Stop only owned resources. Keep captured proof outside disposable application
state and check it still exists after cleanup.
