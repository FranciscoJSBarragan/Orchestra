## Orchestra routing

Keep the root responsible for specification alignment, tier recommendation, capability routing, compact synthesis, the local plan, blockers, ordinary reversible in-scope decisions, phase commits, direct PR observation, and final judgment. The user chooses the active tier and remains the final authority after a concise recommendation and warning. Orchestra is an explicit planned-work route, not the default implementation route. Activate `$orchestra` only through an explicit `$orchestra` invocation or an unequivocal imperative to use or start Orchestra. Ordinary plan requests, descriptive mentions, and direct change, fix, or implementation work remain outside Orchestra. If Orchestra is invoked in a planning-only host mode, reuse conversation context, identify the candidate checkpoint, and pause before branch, worktree, plan, implementation, or commit mutation; continue without a second invocation once the host is execution-capable. Use `$orchestra-phase-commit` only after review and verification pass, then route delivery through `$orchestra-delivery-policy`. Use `${CODEX_HOME:-$HOME/.codex}` as the installed Codex root. For each dispatch, resolve `tiers.<tier>.<capability>` from `${CODEX_HOME:-$HOME/.codex}/orchestra/roles.toml`, load its namespaced `profile` from `${CODEX_HOME:-$HOME/.codex}/agents/`, and pass the entry's explicit `model` and `reasoning_effort`. Compose only the internal references named by `$orchestra`.

Orchestra observes the current host mode and never changes it into a planning-only mode.

Reuse the preceding conversation and first obtain a minimum brief: objective, visible result, approximate repository area, known critical risks, and bounded factual open questions. Ask for a missing objective before creating resources; an explicitly brainstorming-only request remains read-only until formal task setup is authorized. Recommend standard or critical with one-line risk and cost-benefit evidence, then obtain the user's explicit tier choice; standard may be chosen after a critical recommendation without waiving separate high-impact authority gates. Perform a short read-only Git and execution-readiness preflight, read delivery policy, recommend `current_branch`, `orchestra_worktree`, or `codex_worktree` with compatible delivery paths and bootstrap cost, and obtain the user's explicit environment choice before resources, `repository_context`, or formal planning. An explicit instruction after its scope, warning, plan, or pending action satisfies that unchanged checkpoint without duplicate confirmation. Continue the dialogue from focused repository evidence, request only newly material context deltas, close each one-shot analyst after consuming its result, then confirm Objective, User-visible behavior, Constraints, one to three observable Acceptance journeys, Exclusions, Decisions, and Open questions and recommend any tier change before formal planning; the user chooses. Final specification confirmation is the plan-drafting checkpoint; it does not authorize implementation. Do not persist the provisional specification or an unapproved plan. After formal-plan approval, write the exact approved plan directly as `active` at `git rev-parse --git-path orchestra/plan.md`; only `active`, `blocked`, and `completed` are valid. Record active tier, any different recommendation in Decisions, execution mode, checkout path, initial branch and HEAD, base branch and revision, and authorized preexisting changes. When adoption applies, also record adopted source revision, imported paths, existing commit range, and remaining phases. Approval permits reviewed phase commits, not merge, delivery, deployment, or release. Profiles never write the plan. Keep transient compact packets and consecutive clean PR heads in memory or system temporary storage, avoid full-history forks without demonstrated need, reuse context deltas, return accepted findings to the same implementation owner, and resume local failures locally. Keep the implementation owner, reviewer, and one verifier per used verification capability open through their phase; close one-shot analysts after consuming their result. The first review covers the complete bounded target and later reviews cover the meaningful delta. Before phase commit, stop only known Orchestra-owned temporary processes and task tabs, consume cleanup results, and close every phase agent and descendant. Write-capable leftovers block commit; a source-read-only tab cleanup failure is partial. The root uses direct Git for phase commits by default and `commit_phase.py` only when exact-path staging is useful; cleanup is not part of either commit path. It invokes `pr.py observe` directly. Neither operation is an agent capability, and isolated mechanical Git failures stay root-local. Read explicit repository policy and task direction before hold, PR, or local delivery. Opening a PR authorizes review/fix/commit/push until clean but never merge; merge requires separate authority. Never install or synchronize these managed sources during ordinary task execution.

The confirmed execution environment is the only task checkout. `current_branch` creates or switches nothing, permits only one active Orchestra plan per checkout, requires all preexisting changes to belong unambiguously to the task, and requires a warning plus explicit confirmation on the integration base. `orchestra_worktree` creates the collision-free `orchestra/<slug>[-N]` sibling worktree and uses `adopt_worktree.py` only for selected dirty imports. `codex_worktree` reuses only a clean registered worktree under `${CODEX_HOME:-$HOME/.codex}/worktrees` that belongs to the same repository as a distinct base checkout; create the collision-free task branch in place when detached, and block custom roots, existing ambiguous branches, dirty state, or identity conflicts without hidden fallback. Reuse requires exact plan/Git agreement on execution mode, path, branch, base, and HEAD. Hold and open PR retain resources. Local integration rejects `current_branch`; authorized cleanup removes Orchestra-owned worktrees, leaves Codex-owned worktrees clean and detached without deleting their directories, and preserves current-branch checkouts. Incomplete intended post-mutation cleanup is `partial`; intentional retention is success.

For every dispatch, attempt the installed model first. Only `repository_context` may use Luna with reasoning `high` when its assigned model is rejected before execution as unsupported by the internal subagent runtime. Record the substitution only in root memory; create no visible task, persist no fallback, alter no matrix, and return `blocked` for unsupported assigned models on every other capability. The user may change tier in either direction. At a safe transition, finish the current tool call, collect revision, dirty diff, evidence, progress, pending work, and owned resources, stop those resources, close only agents whose assignment changes, update the active tier and Decisions, and spawn replacements only when needed with a compact continuation packet. Do not revert, restart, or create an artificial commit. Preserve evidence for the unchanged revision and target only new risk deltas.

Browser packets use `browser_route: auto | in_app | chrome`: explicit selection must be attempted even as a tool canary and is fixed unless fallback is authorized; an agent may report its blocker but may not veto or substitute it. `auto` prefers Codex's in-app Browser and falls back to Computer Use with Chrome only for a technical capability gap, repeating the complete scenario in a separate task tab. Packets name test-data provenance, reset, safe identifiers, cleanup, and generated paths. Tests run sandboxed unless elevation is declared. Elevate one exact retry only when sandbox, permission, filesystem, network, socket, service, cache, or genuinely ambiguous evidence could explain the failure; do not elevate deterministic syntax, type, compile, lint, import, assertion, validation-contract, or CLI-usage failures.

Report only material transitions, findings or decisions, blockers, fresh verification, and authority requests. State current result, evidence, and next action without routine model/profile plumbing. At completion distinguish implementation-complete from delivered and include location, run or demo instructions, fresh evidence, safe test data, limitations, delivery state, and next authority.
