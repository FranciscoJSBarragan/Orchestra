## Orchestra routing

Keep the root responsible for framing, tiering, user alignment, capability routing, compact synthesis, the local plan, blockers, ordinary reversible in-scope decisions, phase commits, direct PR observation, and final judgment. The root uses its current session configuration selected outside Orchestra and has no assignment. Route light, standard, and critical changes through `$orchestra`; use `$orchestra-phase-commit` only after review and verification pass, then route delivery through `$orchestra-delivery-policy`. Use `${CODEX_HOME:-$HOME/.codex}` as the installed Codex root. For each dispatch, resolve `tiers.<tier>.<capability>` from `${CODEX_HOME:-$HOME/.codex}/orchestra/roles.toml`, load its `profile` from `${CODEX_HOME:-$HOME/.codex}/agents/`, and pass the entry's explicit `model` and `reasoning_effort`. Compose only the internal references named by `$orchestra`.

Treat ambiguity or risk as at least standard. Require explicit user approval before standard or critical implementation; approval permits reviewed phase commits, not merge, delivery, deployment, or release. For planned work, the root maintains `git rev-parse --git-path orchestra/plan.md` with only `draft`, `active`, `blocked`, or `completed`; profiles never write it. Keep packets and consecutive clean PR heads in memory, reuse context deltas, return accepted findings to the same implementation owner, and resume local failures locally. The root invokes `commit_phase.py` and `pr.py observe` directly; neither is an agent capability. Read explicit repository policy and task direction before hold, PR, or local delivery. Opening a PR authorizes review/fix/commit/push until clean but never merge; merge requires separate authority. Never install or synchronize these managed sources during ordinary task execution.

The root solely owns Graphify as advisory, non-blocking context for standard and critical planned work; light never auto-adopts it. Before planning, check command availability and the exact three tracked `graphify-out/` outputs and ignored-data boundary. A missing command or incorrect exact tracked/ignored boundary adds the one approval-gated bootstrap. Only when the command exists, interpret exactly one `graphify hook status` result: valid installed hooks continue; valid absence adds that bootstrap only when the resolved `core.hooksPath` or `git rev-parse --git-path hooks` destination is outside the tracked worktree and no tracked hook would change; failure or uninterpretable output is `partial` source fallback without bootstrap. After hook configuration passes, check the relevant Git delta and pending evidence before query/use and never call status again in that pass. Tell `repository_context` whether the pass found a usable graph; it must otherwise use source and must always verify graph claims against source.

Nothing mutates before approval. An approved bootstrap runs `uv tool install --upgrade graphifyy`, one full `graphify .` build, enforces exactly `graph.json`, `graph.html`, and `GRAPH_REPORT.md` as tracked outputs, and reviews, verifies, and commits that snapshot before any safe native `graphify hook install`; then rerun one complete detection pass. Unsafe hooks, stale or pending evidence, query/hook failure, missing external authority, and later failures are `partial` source fallback and never repeat bootstrap. Never run `graphify codex install` or add a Graphify profile, capability, helper, playbook, wrapper, schema, lock, transaction, state machine, policy gate, or plan status. After functional commits and before `completed`, run `graphify . --update` at most once; commit exactly changed tracked Graphify outputs in one separate graph-only commit or record `nothing_to_commit`. Graphify never establishes correctness or policy, and any failure still permits functional completion.
