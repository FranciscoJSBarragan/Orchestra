## Orchestra routing

Keep the root responsible for specification alignment, tiering, capability routing, compact synthesis, the local plan, blockers, ordinary reversible in-scope decisions, phase commits, direct PR observation, and final judgment. Orchestra is an explicit planned-work route, not the default implementation route. Activate `$orchestra` only through an explicit `$orchestra` invocation or an unequivocal imperative to use or start Orchestra. Ordinary plan requests, descriptive mentions, and direct change, fix, or implementation work remain outside Orchestra. If Orchestra is invoked in a planning-only host mode, reuse conversation context, identify the candidate checkpoint, and pause before branch, worktree, plan, implementation, or commit mutation; continue without a second invocation once the host is execution-capable. Use `$orchestra-phase-commit` only after review and verification pass, then route delivery through `$orchestra-delivery-policy`. Use `${CODEX_HOME:-$HOME/.codex}` as the installed Codex root. For each dispatch, resolve `tiers.<tier>.<capability>` from `${CODEX_HOME:-$HOME/.codex}/orchestra/roles.toml`, load its `profile` from `${CODEX_HOME:-$HOME/.codex}/agents/`, and pass the entry's explicit `model` and `reasoning_effort`. Compose only the internal references named by `$orchestra`.

Reuse the preceding conversation, ask only genuine specification gaps, and confirm Objective, User-visible behavior, Constraints, Acceptance, Exclusions, Decisions, and Open questions before tiering. Use only standard or critical. Do not persist the provisional specification or an unapproved plan. After formal-plan approval, write the exact approved plan directly as `active` at `git rev-parse --git-path orchestra/plan.md`; only `active`, `blocked`, and `completed` are valid. When adoption applies, record adopted source revision, imported paths, existing commit range, and remaining phases. Approval permits reviewed phase commits, not merge, delivery, deployment, or release. Profiles never write the plan. Keep transient packets and consecutive clean PR heads in memory or system temporary storage, reuse context deltas, return accepted findings to the same implementation owner, and resume local failures locally. The root invokes `commit_phase.py` and `pr.py observe` directly; neither is an agent capability. Read explicit repository policy and task direction before hold, PR, or local delivery. Opening a PR authorizes review/fix/commit/push until clean but never merge; merge requires separate authority. Never install or synchronize these managed sources during ordinary task execution.

After specification confirmation and tiering, create a new collision-free task branch and dedicated sibling worktree before repository analysis. Never adopt the current worktree for a new task. Never mutate the source checkout. Fresh work starts at the integration base; adopted committed work starts at the adopted source HEAD while retaining that base; scoped dirty paths import through `adopt_worktree.py`. Use the exact task worktree for every capability and task mutation. Reuse is limited to the same live pre-approval task or an exact approved-plan/Git identity match. Rejected planning removes only resources proven clean and unchanged from the captured base or adopted revision. Hold, open PR, and pending authority retain their resources. Authorized local integration or PR merge cleans only the exact verified task worktree and branches; incomplete post-mutation cleanup is `partial`.
