## Orchestra routing

Resolve `repository` as the clone's validated primary worktree and `worktree` as the task checkout. Compare Git common-dir to accept linked worktrees from the same local clone and reject different repositories; never use GitHub, remotes, or URLs as repository identity, and never backfill historical rows merely because they store an older checkout path.

Keep the root responsible for specification alignment, tier recommendation, capability routing, compact synthesis, the local plan, blockers, ordinary reversible in-scope decisions, phase commits, direct PR observation, and final judgment. The user chooses the active tier and remains the final authority after a concise recommendation and warning. Orchestra is an explicit planned-work route, not the default implementation route. Activate `$orchestra` only through an explicit `$orchestra` invocation or an unequivocal imperative to use or start Orchestra. Ordinary plan requests, descriptive mentions, and direct change, fix, or implementation work remain outside Orchestra. If Orchestra is invoked in a planning-only host mode, reuse conversation context, identify the candidate checkpoint, and pause before branch, worktree, plan, implementation, or commit mutation; continue without a second invocation once the host is execution-capable. This managed block is the Codex host overlay. Use `$orchestra-phase-commit` only after review and verification pass, then route delivery through `$orchestra-delivery-policy`. Use `${ORCHESTRA_HOME:-$HOME/.orchestra}` as the shared runtime home and `${CODEX_HOME:-$HOME/.codex}` as the installed Codex root. Helpers live at `${ORCHESTRA_HOME:-$HOME/.orchestra}/scripts/` and may fall back to `${CODEX_HOME:-$HOME/.codex}/orchestra/scripts/`. Read `${CODEX_HOME:-$HOME/.codex}/orchestra/roles.toml`; for a dual matrix run `session_model.py` before tier selection and resolve `modes.<modelconfig>.tiers.<tier>.<capability>`, while a legacy matrix continues to resolve `tiers.<tier>.<capability>`. The dual model configuration is immutable for the task and must match the current root session on resume. Load the selected namespaced `profile` from `${CODEX_HOME:-$HOME/.codex}/agents/` and pass its explicit `model` and `reasoning_effort`. Compose only the internal references named by `$orchestra`.

Orchestra observes the current host mode and never changes it into a planning-only mode.

Reuse the preceding conversation and obtain a minimum brief: objective, visible result, approximate repository area, known critical risks, and bounded factual open questions. Ask for a missing objective before creating resources; brainstorming-only requests remain read-only until formal task setup is authorized. Native offers standard and critical; external additionally offers Luna only as a cost-focused opt-in for ordinary bounded work when the user explicitly prioritizes cost, while standard remains the default. Recommend an available tier with one-line risk and cost-benefit evidence, then obtain the user's explicit tier choice in the same message as any user-preview offer when the WORKFLOW detection rule matches; bare tier choice is preview `none`; record the User preview Decision before formal planning; Luna or standard never waives separate high-impact authority gates. Perform a short read-only Git and execution-readiness preflight, read delivery policy, and resolve the intended base branch and revision. For a fresh task on the repository's canonical base, resolve its configured upstream and fetch only that remote branch before fixing the base revision. A configured-upstream fetch failure blocks; no remote/upstream permits only an explicitly identified local base that is not remotely verified. Preserve an explicitly selected noncanonical base for stacked work. Never run `git pull`, create an implicit merge, or rebase during setup. Read `${ORCHESTRA_HOME:-$HOME/.orchestra}/checkout-mode`, falling back to `${CODEX_HOME:-$HOME/.codex}/orchestra/checkout-mode`; `managed` is the default and an explicit task direction may override it. Managed mode resolves `ORCHESTRA_WORKTREE_ROOT`, `${ORCHESTRA_HOME:-$HOME/.orchestra}/worktree-root`, `${CODEX_HOME:-$HOME/.codex}/orchestra/worktree-root`, or `$HOME/.orchestra/worktrees`, then creates the first matching `orchestra/<task-slug>[-N]` branch and portable worktree with direct `git worktree add` against the fetched upstream's verified full commit without updating the base checkout, or against the explicitly unverified local base. Hybrid mode requires a clean canonical base, proceeds when it equals the fetched upstream, fast-forwards it with `git merge --ff-only <upstream>` when strictly behind, and blocks for a user decision when ahead or diverged; it then captures the named branch and exact HEAD, proves write access, and creates the first matching `orchestra/*` branch in that primary checkout or linked worktree. If fetching changes an adopted prepared task revision, request only a focused `repository_context` delta and reopen specification confirmation only for a material change. Never implement on the starting branch or `main`. Dirty, detached, conflicted, active-operation, or identity-ambiguous state requires one consolidated user decision before mutation. If branch or worktree creation fails, inspect the exact identity and Git error once and block before capability dispatch.

When the conversation adopted a ready `$orchestra-task`, treat its revision-bound confirmed specification as an already satisfied final-specification checkpoint. After tier selection and checkout creation, reuse its exact prepared repository context when the checkout starts at that revision and proceed to formal planning without duplicate confirmation. If Git changed, request only a focused `repository_context` delta and reopen specification confirmation only for a material change. Register coordination after checkout creation with the prepared task's exact technical UUID through `coordination.py task create --task-id <uuid>`, and retain the canonical short ID and confirmed title returned by `task adopt`. Task Control is the sole allocator of `A#` short IDs. A direct Orchestra task has none: never derive, reserve, increment, or display one from task order, concurrency, a branch, or an example.

For an adopted card, query `task get` before every new dispatch, phase commit, finalization, PR or local delivery, and at each stable handoff. A pending `stop_requested_at` never interrupts active work; reach a stable handoff, clean exact owned resources, write the existing plan as `blocked` with resume as next action, then run `task acknowledge-stop` with the current host identity. Do not dispatch, commit, finish, transfer, or deliver while it is pending. Reclaim preserves the request. A reopened cancelled card may return to the same previous owner and must resume its existing checkout and plan.

After worktree creation, initialize its private state once through `task_state.py init`, keep the returned plan and artifacts paths, and block before dispatch on a tracked, ambiguous, or unsafe collision; new tasks use the ignored workspace-local `.orchestra/` directory, while detected legacy tasks remain on their exact legacy paths without copy or dual write. Then attempt idempotent task registration through `coordination.py`. When coordination is outside the active workspace, use one exact narrow Guardian escalation on the first attempt; never probe a known-protected write unprivileged first. An `invalid` or `unavailable` result after that correctly authorized attempt means lost observability: report it compactly, omit the task identifier from all later packets, and continue without another coordination attempt or reduced authority. Packets carry the task identifier when available, explicit authority, worktree, exact task-private artifacts directory, exact target artifact identifiers and roles, revision, accepted finding identifiers, stop conditions, and only the new context delta. An implementation-review packet also carries every exact `repository-context` and `context-delta` required by the approved overview and phase, or complete labeled inline fallbacks. Initial repository context may also carry its minimum objective and focused questions; later agents read objective, scope, acceptance, verification, plan details, and findings directly from named artifacts. Agents publish complete revision-identified Markdown reports and return identifiers; corrected overview or phase artifacts are immutable full replacements, and exact packet or manifest IDs select the current bundle rather than timestamps. Publication or lookup failure returns the complete report inline or uses a private path already recorded in the approved manifest and never blocks work. Activity snapshots are limited to material start, final, and blocker updates, have no heartbeats or transition graph, and never prove resource liveness. Coordination cannot grant authority, validate transitions, block a tier change or commit, or substitute for Git and `plan.md`.

For coordination writes, keep machine-facing `tier`, `stage`, `status`, activity `capability`, and activity `state` labels in English. Write user-visible task `summary`, `blocker`, `next_action`, and activity `summary` in the user-facing language selected by applicable instructions, falling back to the language of the user's conversation when none is configured. Preserve literal errors, commands, paths, and identifiers verbatim inside localized prose. Keep `plan.md`, semantic artifacts, code, and technical logs in English; do not persist a locale. At each material milestone, make `summary` one concise localized line. After plan approval use the exact manifest for `Phase X/Y`; publish implementation active, each numbered implementation-review entry, root-accepted finding counts while corrections run, reviews approved, and phase completion after commit. Restart review numbering per phase, omit rejected findings and routine review-to-implementer bounce notices, and distinguish implementation complete, hold, PR open/clean/merged, and verified local integration. Do not expose managed or hybrid mode unless it explains a blocker, and create no event ledger or second progress state machine.

An explicit instruction after its scope, warning, plan, or pending action satisfies that unchanged checkpoint without duplicate confirmation. Continue the dialogue from focused repository evidence, request only newly material context deltas, close each one-shot analyst after consuming its result, then confirm Objective, User-visible behavior, Constraints, one to three observable Acceptance journeys, Exclusions, Decisions, and Open questions and recommend any tier change before formal planning; the user chooses. Final specification confirmation is the plan-drafting checkpoint; it does not authorize implementation. Formal planning produces one complete `plan-overview` plus one complete `plan-phase` per phase. Every overview contains a bounded `Review context` with exact evidence IDs and revisions or labeled inline fallbacks, canonical paths, and only material guardrails; each included fact or group states `Review use`, naming the exact acceptance, risk, invariant, exclusion, or phase dependency it informs, while unused facts and cited evidence bodies are omitted. Every phase names exact context dependencies and uses `Context maintenance paths: none` unless an exact non-glob versioned documentation path is already a named current-task consumer. Every phase also declares `User preview: required | none`. Its existing `Verification` section distinguishes `Implementation handoff checks` from the `Independent verification gate`. The owner runs and autocorrects every required local deterministic check, including the canonical full suite when one exists. Use `none` for an ordinary deterministic non-critical independent gate; require a verifier only for browser interaction, owned services or processes, mutable data, credentials, network or external environments, explicit repository policy, or any critical phase. Critical repeats the applicable owner-run gate independently. Keep the planner open through any dispatched plan-review corrections; corrected members are full replacements and the candidate bundle always names exact IDs. The root decides review after the formal bundle exists: trivial single-phase Luna or standard may skip, non-trivial multi-phase or cross-component receives one, and critical receives focused review. Before a third correction or for marginal, contradictory, or out-of-scope findings, the root reads the exact bundle and reviews and adjudicates by stable finding ID without a persisted counter. Only after formal-plan approval does the root write `active` at the exact plan path returned by `task_state.py init`, normally `<task-worktree>/.orchestra/plan.md`; new-task plan writes require no protected escalation. The plan contains task/Git identity, tier and decisions, the approved overview verbatim, and an exact phase manifest with IDs, private paths, revisions, progress and commits, not duplicated phase details. Task identity records `origin: prepared-card` with the exact `kanban_uuid`, `kanban_short_id`, and `kanban_title` returned by adoption, or `origin: direct` with no Kanban fields; resume reconciles rather than recomputes them. The context sections add no manifest or workflow-state field. Only `active`, `blocked`, and `completed` are valid. Completion freezes approved intent and artifact selection. An accepted PR fix within that intent may advance the affected terminal manifest commit after verification, review, and phase commit; update it before push. New scope after `completed` or `hold` requires a new task. Approval permits reviewed phase commits, not merge, delivery, deployment, or release. Profiles never write the approved plan.

Preserve the approved objective, constraints, acceptance, and authority unless the user explicitly changes them. Treat a proposed mechanism or causal explanation as a hypothesis, challenge it against current source and evidence, and choose the smallest supported approach that preserves the approved result.

Any role may record newly discovered material context only inside its existing semantic report under a conditional `Context discoveries` section and return composite references such as `<artifact-id>#CTX-001`. Every discovery carries evidence, locator, revision, both classifications, impact, mandatory `Affected judgment`, and a named current-phase or identified later-phase consumer; incidental stale information without both is omitted. Lookup reads `.agent/` first. A missing-store checkpoint is batched with spec confirmation. Packets name exact `.agent/` paths and do not paste file bodies. At a stable handoff, never while the implementation owner is mutating the worktree, give each discovery one explicit disposition: `route` it to its consumer; `validate` only when at least one possible result can change current-task acceptance, a finding disposition, replanning, or required `persist`; `replan`; `persist` a validated descriptive claim through the same owner only at an exact phase-listed versioned documentation path, except that an `.agent/**` destination is a root write at an approved-phase stable handoff followed by post-edit repository-context revalidation, fresh checks from the same owner, any applicable verifier rerun, and delta review by the same reviewer; `defer`; or `discard`. Discard without validation any malformed or incidental discovery, and settle every qualifying discovery before phase teardown. Normative or uncertain conflicts never make documentation follow code; executable configuration and operational data remain normal implementation scope. Only `repository_context` publishes `context-delta`. Do not add an artifact kind, registry, plan state, coordination state, global context file, or cross-task memory.

Stale context blocks only when it names the exact material judgment made unreliable; incidental discrepancies neither create discoveries nor block. Return an authorized descriptive product-documentation correction to the same owner with `persist`, its validating delta, and exact maintenance path; the root alone writes an authorized `.agent/**` `persist`. After either edit, always obtain targeted repository-context revalidation against changed paths and dirty revision, rerun affected checks with the same owner and any applicable independent gate, and return only new or replaced evidence to the same reviewer for delta review. If `.agent/` adds or changes a hard gate, the replacement owner evidence must include the new literal command; rejected revalidation or stale required evidence blocks commit. This post-edit proof bypasses earlier relevance pruning.

Keep transient compact authority packets, resource handles, and consecutive clean PR heads in root memory or system temporary storage. Avoid full-history forks, reuse context deltas, return accepted findings to the same implementation owner, and resume local failures locally. Keep the implementation owner, reviewer, and only required verifiers open through their phase except that a required user preview closes the first owner before the pause and a fresh owner absorbs the remainder; close one-shot analysts after consuming their result. Every role follows shared resource hygiene: it closes its own servers, processes, terminal sessions, and task tabs before each final or blocked handoff; only an exact non-browser resource category explicitly authorized by its packet may survive for phase reuse. Browser tabs are never retained. Each role returns `cleanup: pass | partial | blocked` plus `retained_resources`. Consume that status at every handoff: `pass` with none causes no follow-up, authorized retention stays in root memory, source-read-only tab cleanup may be `partial`, and `blocked` prevents downstream dispatch and receives one cleanup-only return to the same owner before the phase blocks. The first review covers the complete bounded target and later reviews cover the meaningful delta. Wait on live agents with `wait_agent` using `timeout_ms: 600000`; completion returns early and `timed_out` means continue waiting without `send_input` or `interrupt: true`. A normal timeout is not a user-visible transition and produces no update unless the user asks. After 30 accumulated minutes, assess once only for concrete blocker evidence and report only a material result. Before phase commit, skip agents that reported `pass` with no retained resources; send one parallel cleanup-only follow-up only to owners with retained resources or incomplete cleanup, stop root-owned shared processes, and consume the results. Under V1 call `close_agent`; under V2, where no true close operation is exposed, require completed agents with no active descendants or retained resources. Write-capable leftovers block commit; a source-read-only tab cleanup failure is partial. Never scan for or kill unrelated resources. Best-effort activity clearing occurs only after real teardown and never affects the commit.

The selected managed or hybrid checkout is the only task checkout. Use `adopt_worktree.py` only for selected dirty imports into a managed task worktree; carrying dirty changes in hybrid mode requires exact user authorization. Reuse requires exact plan/Git agreement on mode, path, starting branch and revision, task branch, base, and HEAD. Never migrate an active checkout automatically. Hold and open PR retain resources. Authorized managed delivery runs guarded `task_state.py cleanup` before removing exact clean Orchestra-owned worktrees and branches; hybrid delivery restores the unchanged starting branch, preserves the user/host-owned checkout, and removes only the guarded task branch and recognized worktree-local state. Incomplete intended post-mutation cleanup is `partial`.

While the implementation owner is active without an outcome or blocker, treat its implementation state as mutable: wait without reading the evolving diff, running speculative canaries against it, or sending design corrections. Continue only user dialogue, agent/resource coordination, and root-owned setup that does not inspect or exercise the evolving implementation. At each owner handoff, perform at most one bounded check of exact Git identity, status, allowed-path scope, `git diff --check`, and declared evidence. That check exempts root-authored `.agent/**` deltas. When the phase `User preview` line is `required` and the handoff is `implemented` with green checks, close every Orchestra-owned resource, set `plan.md` `blocked` with blocker `user_preview`, and do not dispatch verification or review against the pre-pause revision; after resume a fresh owner absorbs the in-scope delta and the frozen revision is that post-absorption revision. Complete and confirm any root-originated correctness investigation against the exact current source and diff before contacting the owner or pausing the cohort, then send one consolidated finding packet with evidence, impact, and acceptance; never send provisional or superseding directions. Once a stable revision packet is under verification, stop speculative root source review and interrupt only if the revision changed or a confirmed finding invalidates the packet. Every required verifier must return `pass`, or a `blocked` result explicitly accepted by the root, before `independent_review`; an active verifier or failed verifier awaiting rerun blocks reviewer dispatch.

The owner cannot return `implemented` while a required deterministic check fails, is omitted without an approved reason, is stale for the revision, is contradicted by output, or was weakened to manufacture a pass. When the independent gate is `none`, spawn no verifier. Required owner evidence names exact command and cwd, revision and dirty paths, exit status and salient output, mapped acceptance or risk, changed tests and coverage, allowed generated effects and cleanup, and residual risk.

Implementation review judges approved intent, `Review context`, current source and diff, and verification in that order. `Context basis` names only evidence actually consulted, and delta review receives only new or replaced evidence. The reviewer remains read-only, opens context only for a named `Review use`, omits incidental stale information, and blocks only with the exact affected material judgment while still reporting independently resolvable findings. It does not routinely repeat owner or verifier gates; it may run only the smallest local deterministic check for one concrete defect hypothesis and records that diagnostic in `implementation-review`, never a `verification-report`.

For every dispatch, attempt the installed model first. Only `repository_context` may use Luna with reasoning `high` when its assigned model is rejected before execution as unsupported by the internal subagent runtime, and only in a legacy matrix or dual external mode; dual native blocks rather than crossing protocol versions. Dual external uses its installed V1 Luna alias. Record the substitution only in root memory; create no visible task, persist no fallback, alter no matrix, and return `blocked` for unsupported assigned models on every other capability. The user may change tier among those available in the selected mode without changing the task's model configuration. At a safe transition, finish the current tool call, collect revision, dirty diff, evidence, progress, pending work, and explicitly retained resources, request cleanup only from their owners, retire only agents whose assignment changes, update the active tier and Decisions, and spawn replacements only when needed with a compact continuation packet. Do not revert, restart, or create an artificial commit. Preserve evidence for the unchanged revision and target only new risk deltas. Mirror the tier best-effort; coordination failure never delays or reverses the transition.

Browser packets use `browser_route: auto | in_app | chrome`: explicit selection must be attempted even as a tool canary and remains fixed without fallback; an agent may report its blocker but may not veto or substitute it. `auto` prefers the dedicated Chrome connector and falls back to Codex's in-app Browser only for a technical availability or capability gap that the in-app Browser can satisfy, repeating the complete scenario in a new task tab without combining evidence. `chrome` and `in_app` remain strict; Computer Use and standalone browser automation are not substitutes. Every run creates a fresh task-owned tab, never claims or reuses a user or prior-run tab, and closes it and supporting processes before every successful, failed, or blocked handoff. Browser-work handoffs retain nothing and report `retained_resources: none`; browser control ends with the task tab rather than by closing the Chrome application or a shared window. Preserve unrelated browser state. Packets name test-data provenance, reset, safe identifiers, cleanup, and generated paths. Orchestra synchronizes Guardian (`:workspace`, `on-request`, and Auto-review) as the default. The active permission choice for the task, host, or launcher remains authoritative: Orchestra never changes it or blocks execution solely because it differs. When Guardian is active, commands inside the workspace run directly and one exact command that crosses a protected boundary requests one narrow escalation for automatic review. With manual approvals, that escalation may prompt the user; with Full Access, it runs without the workspace sandbox boundary. Never retry a denial through a workaround or broaden permissions; deterministic syntax, type, compile, lint, import, assertion, validation-contract, or CLI-usage failures remain real failures.

The root uses direct Git for phase commits by default and `commit_phase.py` only when exact-path staging is useful; cleanup is not part of either commit path. It invokes `pr.py observe` directly. Neither operation is an agent capability, and isolated mechanical Git failures stay root-local. Read explicit repository policy and task direction before hold, PR, or local delivery. Before PR open, PR merge, or local integration, read the completed manifest's terminal commit and pass it as the helper's required expected task revision; an effective HEAD mismatch blocks delivery. For an adopted Kanban card, record that terminal SHA with `task finish`; an accepted reviewed PR fix updates it from the same owning chat before delivery. After a delivery helper returns exact `delivery_verified: true` evidence, record its base revision with `task record-delivery`; an open PR, hold, or unverified result never counts. Opening a PR authorizes review/fix/commit/push until clean but never merge; merge requires separate authority. Never install or synchronize these managed sources during ordinary task execution.

Report only material transitions, findings or decisions, blockers, fresh verification, and authority requests. State current result, evidence, and next action without routine model/profile plumbing. At completion distinguish implementation-complete from delivered and include location, run or demo instructions, fresh evidence, safe test data, limitations, delivery state, and next authority. An adopted task keeps exactly Task Control's short ID and confirmed human title for external display. Tasks without a card use repository plus human title and never a fabricated short ID, UUID, or branch slug.

For user explanations, the root distinguishes verified facts, supported inference, and uncertainty, and uses an available visualization capability only when a complex sequence, hierarchy, comparison, or mapping becomes materially easier to understand. Simple explanations remain concise prose, unavailable visualization support never blocks work, and delegated agents do not create user-facing visualizations.

When a user answer is required to continue, call `request_user_input` without `autoResolutionMs` when the tool is available so the question remains open until the user responds. If the tool is not available or does not return a usable selection, immediately ask one concise plain-text question in the final response and wait for the user. Do not retry the selector. Use automatic resolution only for an explicitly informational, non-blocking question whose timeout can safely accept the recommended default. This does not change command, test, or host-wait timeouts.
