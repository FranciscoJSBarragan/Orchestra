## Orchestra routing

Keep the root responsible for specification alignment, tiering, capability routing, compact synthesis, the local plan, blockers, ordinary reversible in-scope decisions, phase commits, direct PR observation, and final judgment. Orchestra is an explicit planned-work route, not the default implementation route. Activate `$orchestra` only through an explicit `$orchestra` invocation or an unequivocal imperative to use or start Orchestra. Ordinary plan requests, descriptive mentions, and direct change, fix, or implementation work remain outside Orchestra. If Orchestra is invoked in a planning-only host mode, reuse conversation context, identify the candidate checkpoint, and pause before branch, worktree, plan, implementation, or commit mutation; continue without a second invocation once the host is execution-capable. Use `$orchestra-phase-commit` only after review and verification pass, then route delivery through `$orchestra-delivery-policy`. Use `${CODEX_HOME:-$HOME/.codex}` as the installed Codex root. For each dispatch, resolve `tiers.<tier>.<capability>` from `${CODEX_HOME:-$HOME/.codex}/orchestra/roles.toml`, load its `profile` from `${CODEX_HOME:-$HOME/.codex}/agents/`, and pass the entry's explicit `model` and `reasoning_effort`. Compose only the internal references named by `$orchestra`.

Orchestra observes the current host mode and never changes it into a planning-only mode.

Reuse the preceding conversation and first obtain a minimum brief: objective, visible result, approximate repository area, known critical risks, and bounded factual open questions. Ask for a missing objective before creating resources; an explicitly brainstorming-only request remains read-only until formal task setup is authorized. Declare an initial standard or critical tier, create the isolated task resources, and dispatch focused `repository_context`. Continue the dialogue from that evidence, request only newly material context deltas, close each one-shot analyst after consuming its result, then confirm Objective, User-visible behavior, Constraints, Acceptance, Exclusions, Decisions, and Open questions and revalidate the tier before formal planning. Final specification confirmation is the plan-drafting checkpoint; it does not authorize implementation. Do not persist the provisional specification or an unapproved plan. After formal-plan approval, write the exact approved plan directly as `active` at `git rev-parse --git-path orchestra/plan.md`; only `active`, `blocked`, and `completed` are valid. When adoption applies, record adopted source revision, imported paths, existing commit range, and remaining phases. Approval permits reviewed phase commits, not merge, delivery, deployment, or release. Profiles never write the plan. Keep transient packets and consecutive clean PR heads in memory or system temporary storage, reuse context deltas, return accepted findings to the same implementation owner, and resume local failures locally. Keep the implementation owner, reviewer, and one verifier per used verification capability open through their phase; close one-shot analysts after consuming their result. Before phase commit, stop only known Orchestra-owned temporary processes and task tabs, consume cleanup results, and close every phase agent and descendant. Write-capable leftovers block commit; a source-read-only tab cleanup failure is partial. The root uses direct Git for phase commits by default and `commit_phase.py` only when exact-path staging is useful; cleanup is not part of either commit path. It invokes `pr.py observe` directly. Neither operation is an agent capability, and isolated mechanical Git failures stay root-local. Read explicit repository policy and task direction before hold, PR, or local delivery. Opening a PR authorizes review/fix/commit/push until clean but never merge; merge requires separate authority. Never install or synchronize these managed sources during ordinary task execution.

After the minimum brief and initial tier, create a new collision-free task branch and dedicated sibling worktree before repository analysis. Never adopt the current worktree for a new task. Never mutate the source checkout. Fresh work starts at the integration base; adopted committed work starts at the adopted source HEAD while retaining that base; scoped dirty paths import through `adopt_worktree.py`. Use the exact task worktree for every capability and task mutation. Reuse is limited to the same live pre-approval task or an exact approved-plan/Git identity match. Rejected or abandoned planning removes only resources proven clean and unchanged from the captured base or adopted revision; otherwise preserve them. Hold, open PR, and pending authority retain their resources. Authorized local integration or PR merge cleans only the exact verified task worktree and branches; incomplete post-mutation cleanup is `partial`.

For every dispatch, attempt the installed model first. Only `repository_context` may use Luna with reasoning `high` when its assigned model is rejected before execution as unsupported by the internal subagent runtime. Record the substitution only in root memory; create no visible task, persist no fallback, alter no matrix, and return `blocked` for unsupported assigned models on every other capability.

Browser packets use `browser_route: auto | in_app | chrome`: explicit selection is fixed unless fallback is authorized; `auto` prefers Codex's in-app Browser and falls back to Computer Use with Chrome only for a technical capability gap, repeating the complete scenario in a separate task tab. Tests run sandboxed unless elevation is declared; before broader verification or diagnosis, rerun any failed test once with the exact command and working directory under elevated permission.
