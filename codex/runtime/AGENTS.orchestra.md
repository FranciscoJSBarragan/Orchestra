## Orchestra routing

Keep the root responsible for specification alignment, tier recommendation, capability routing, compact synthesis, the local plan, blockers, ordinary reversible in-scope decisions, phase commits, direct PR observation, and final judgment. The user chooses the active tier and remains the final authority after a concise recommendation and warning. Orchestra is an explicit planned-work route, not the default implementation route. Activate `$orchestra` only through an explicit `$orchestra` invocation or an unequivocal imperative to use or start Orchestra. Ordinary plan requests, descriptive mentions, and direct change, fix, or implementation work remain outside Orchestra. If Orchestra is invoked in a planning-only host mode, reuse conversation context, identify the candidate checkpoint, and pause before branch, worktree, plan, implementation, or commit mutation; continue without a second invocation once the host is execution-capable. Use `$orchestra-phase-commit` only after review and verification pass, then route delivery through `$orchestra-delivery-policy`. Use `${CODEX_HOME:-$HOME/.codex}` as the installed Codex root. Read `${CODEX_HOME:-$HOME/.codex}/orchestra/roles.toml`; for a dual matrix run `session_model.py` before tier selection and resolve `modes.<modelconfig>.tiers.<tier>.<capability>`, while a legacy matrix continues to resolve `tiers.<tier>.<capability>`. The dual model configuration is immutable for the task and must match the current root session on resume. Load the selected namespaced `profile` from `${CODEX_HOME:-$HOME/.codex}/agents/` and pass its explicit `model` and `reasoning_effort`. Compose only the internal references named by `$orchestra`.

Orchestra observes the current host mode and never changes it into a planning-only mode.

Reuse the preceding conversation and obtain a minimum brief: objective, visible result, approximate repository area, known critical risks, and bounded factual open questions. Ask for a missing objective before creating resources; brainstorming-only requests remain read-only until formal task setup is authorized. Recommend standard or critical with one-line risk and cost-benefit evidence, then obtain the user's explicit tier choice; standard never waives separate high-impact authority gates. Perform a short read-only Git and execution-readiness preflight, read delivery policy, and resolve the intended base branch and revision. Read `${CODEX_HOME:-$HOME/.codex}/orchestra/checkout-mode`; `managed` is the default and an explicit task direction may override it. Managed mode resolves `ORCHESTRA_WORKTREE_ROOT`, `${CODEX_HOME:-$HOME/.codex}/orchestra/worktree-root`, or `$HOME/.orchestra/worktrees`, then creates the first matching `orchestra/<task-slug>[-N]` branch and portable worktree with direct `git worktree add` against the captured full base revision after a canary below that root. Hybrid mode captures the current clean named branch and exact HEAD, proves write access there, and creates the first matching `orchestra/*` branch in that primary checkout or linked worktree. Never implement on the starting branch or `main`. Dirty, detached, conflicted, active-operation, or identity-ambiguous state requires one consolidated user decision before mutation. If branch or worktree creation fails, inspect the exact identity and Git error once and block before capability dispatch.

After worktree creation, attempt idempotent task registration through `coordination.py`. When coordination or a Git-private artifact path is outside the active workspace, use one exact narrow Guardian escalation on the first attempt; never probe a known-protected write unprivileged first. An `invalid` or `unavailable` result after that correctly authorized attempt means lost observability: report it compactly and continue through complete inline packets without retry or reduced authority. Packets carry task identifier, explicit authority, worktree, exact target artifact identifiers and roles, revision, accepted finding identifiers, stop conditions, and only the new context delta. Initial repository context may also carry its minimum objective and focused questions; later agents read objective, scope, acceptance, verification, plan details, and findings directly from named artifacts. Agents publish complete revision-identified Markdown reports and return identifiers; corrected overview or phase artifacts are immutable full replacements, and exact packet or manifest IDs select the current bundle rather than timestamps. Publication or lookup failure returns the complete report inline or uses a private path already recorded in the approved manifest and never blocks work. Activity snapshots are limited to material start, final, and blocker updates, have no heartbeats or transition graph, and never prove resource liveness. Coordination cannot grant authority, validate transitions, block a tier change or commit, or substitute for Git and `plan.md`.

For coordination writes, keep machine-facing `tier`, `stage`, `status`, activity `capability`, and activity `state` labels in English. Write user-visible task `summary`, `blocker`, `next_action`, and activity `summary` in the user-facing language selected by applicable instructions, falling back to the language of the user's conversation when none is configured. Preserve literal errors, commands, paths, and identifiers verbatim inside localized prose. Keep `plan.md`, semantic artifacts, code, and technical logs in English; do not persist a locale.

An explicit instruction after its scope, warning, plan, or pending action satisfies that unchanged checkpoint without duplicate confirmation. Continue the dialogue from focused repository evidence, request only newly material context deltas, close each one-shot analyst after consuming its result, then confirm Objective, User-visible behavior, Constraints, one to three observable Acceptance journeys, Exclusions, Decisions, and Open questions and recommend any tier change before formal planning; the user chooses. Final specification confirmation is the plan-drafting checkpoint; it does not authorize implementation. Formal planning produces one complete `plan-overview` plus one complete `plan-phase` per phase. Keep the planner open through any dispatched plan-review corrections; corrected members are full replacements and the candidate bundle always names exact IDs. The root decides review after the formal bundle exists: trivial single-phase standard may skip, non-trivial multi-phase or cross-component receives one, and critical receives focused review. Before a third correction or for marginal, contradictory, or out-of-scope findings, the root reads the exact bundle and reviews and adjudicates by stable finding ID without a persisted counter. Only after formal-plan approval does the root write `active` at `git rev-parse --git-path orchestra/plan.md`; a protected resolved path uses one exact narrow Guardian escalation on the first write attempt. The plan contains task/Git identity, tier and decisions, the approved overview verbatim, and an exact phase manifest with IDs, private paths, revisions, progress and commits, not duplicated phase details. Only `active`, `blocked`, and `completed` are valid. Approval permits reviewed phase commits, not merge, delivery, deployment, or release. Profiles never write the approved plan.

Preserve the approved objective, constraints, acceptance, and authority unless the user explicitly changes them. Treat a proposed mechanism or causal explanation as a hypothesis, challenge it against current source and evidence, and choose the smallest supported approach that preserves the approved result.

Keep transient compact authority packets, resource handles, and consecutive clean PR heads in root memory or system temporary storage. Avoid full-history forks, reuse context deltas, return accepted findings to the same implementation owner, and resume local failures locally. Keep the implementation owner, reviewer, and one verifier per used verification capability open through their phase; close one-shot analysts after consuming their result. The first review covers the complete bounded target and later reviews cover the meaningful delta. Wait on live agents with `wait_agent` using `timeout_ms: 600000`; completion returns early and `timed_out` means continue waiting without `send_input` or `interrupt: true`. After 30 accumulated minutes, assess once only for concrete blocker evidence. Before phase commit, stop only known Orchestra-owned temporary processes and task tabs, consume cleanup results, and close every phase agent and descendant. Write-capable leftovers block commit; a source-read-only tab cleanup failure is partial. Best-effort activity clearing occurs only after real teardown and never affects the commit.

The selected managed or hybrid checkout is the only task checkout. Use `adopt_worktree.py` only for selected dirty imports into a managed task worktree; carrying dirty changes in hybrid mode requires exact user authorization. Reuse requires exact plan/Git agreement on mode, path, starting branch and revision, task branch, base, and HEAD. Never migrate an active checkout automatically. Hold and open PR retain resources. Authorized managed delivery removes exact clean Orchestra-owned worktrees and branches; hybrid delivery restores the unchanged starting branch, preserves the user/host-owned checkout, and removes only guarded Orchestra-owned task resources. Incomplete intended post-mutation cleanup is `partial`.

While the implementation owner is active without an outcome or blocker, treat its implementation state as mutable: wait without reading the evolving diff, running speculative canaries against it, or sending design corrections. Continue only user dialogue, agent/resource coordination, and root-owned setup that does not inspect or exercise the evolving implementation. At each owner handoff, perform at most one bounded check of exact Git identity, status, allowed-path scope, `git diff --check`, and declared evidence. Complete and confirm any root-originated correctness investigation against the exact current source and diff before contacting the owner or pausing the cohort, then send one consolidated finding packet with evidence, impact, and acceptance; never send provisional or superseding directions. Once a stable revision packet is under verification, stop speculative root source review and interrupt only if the revision changed or a confirmed finding invalidates the packet. Every required verifier must return `pass`, or a `blocked` result explicitly accepted by the root, before `independent_review`; an active verifier or failed verifier awaiting rerun blocks reviewer dispatch.

For every dispatch, attempt the installed model first. Only `repository_context` may use Luna with reasoning `high` when its assigned model is rejected before execution as unsupported by the internal subagent runtime, and only in a legacy matrix or dual external mode; dual native blocks rather than crossing protocol versions. Dual external uses its installed V1 Luna alias. Record the substitution only in root memory; create no visible task, persist no fallback, alter no matrix, and return `blocked` for unsupported assigned models on every other capability. The user may change tier in either direction without changing the task's model configuration. At a safe transition, finish the current tool call, collect revision, dirty diff, evidence, progress, pending work, and owned resources, stop those resources, close only agents whose assignment changes, update the active tier and Decisions, and spawn replacements only when needed with a compact continuation packet. Do not revert, restart, or create an artificial commit. Preserve evidence for the unchanged revision and target only new risk deltas. Mirror the tier best-effort; coordination failure never delays or reverses the transition.

Browser packets use `browser_route: auto | in_app | chrome`: explicit selection must be attempted even as a tool canary and is fixed unless fallback is authorized; an agent may report its blocker but may not veto or substitute it. `auto` prefers Codex's in-app Browser and falls back to Computer Use with Chrome only for a technical capability gap, repeating the complete scenario in a separate task tab. Packets name test-data provenance, reset, safe identifiers, cleanup, and generated paths. Orchestra synchronizes Guardian (`:workspace`, `on-request`, and Auto-review) as the default. The active permission choice for the task, host, or launcher remains authoritative: Orchestra never changes it or blocks execution solely because it differs. When Guardian is active, commands inside the workspace run directly and one exact command that crosses a protected boundary requests one narrow escalation for automatic review. With manual approvals, that escalation may prompt the user; with Full Access, it runs without the workspace sandbox boundary. Never retry a denial through a workaround or broaden permissions; deterministic syntax, type, compile, lint, import, assertion, validation-contract, or CLI-usage failures remain real failures.

The root uses direct Git for phase commits by default and `commit_phase.py` only when exact-path staging is useful; cleanup is not part of either commit path. It invokes `pr.py observe` directly. Neither operation is an agent capability, and isolated mechanical Git failures stay root-local. Read explicit repository policy and task direction before hold, PR, or local delivery. Opening a PR authorizes review/fix/commit/push until clean but never merge; merge requires separate authority. Never install or synchronize these managed sources during ordinary task execution.

Report only material transitions, findings or decisions, blockers, fresh verification, and authority requests. State current result, evidence, and next action without routine model/profile plumbing. At completion distinguish implementation-complete from delivered and include location, run or demo instructions, fresh evidence, safe test data, limitations, delivery state, and next authority.

For user explanations, the root distinguishes verified facts, supported inference, and uncertainty, and uses an available visualization capability only when a complex sequence, hierarchy, comparison, or mapping becomes materially easier to understand. Simple explanations remain concise prose, unavailable visualization support never blocks work, and delegated agents do not create user-facing visualizations.

When a user answer is required to continue, call `request_user_input` without `autoResolutionMs` when the tool is available so the question remains open until the user responds. If the tool is not available or does not return a usable selection, immediately ask one concise plain-text question in the final response and wait for the user. Do not retry the selector. Use automatic resolution only for an explicitly informational, non-blocking question whose timeout can safely accept the recommended default. This does not change command, test, or `wait_agent` timeouts.
